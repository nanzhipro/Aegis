# 为什么这套 plan 能驱动 AI 连续工作 5 小时

AI 在长流程里失败的本质原因只有三个：**上下文会被压缩**、**注意力会漂移**、**没有客观完成标准会自我感觉良好**。Aegis 的 plan 体系不是在"写得更详细"上下功夫，而是**把这三个问题全部外部化到仓库文件和脚本里**，让 AI 只需要在一个很小的窗口里做一件事。

下面先拆机制，再抽象出可复用 workflow。

---

## 一、拆解：它到底靠什么撑住 5 小时

### 1. 把"当前该做什么"从 AI 记忆里剥离出来

传统做法是一份大 Plan.md，AI 边做边判断"我到哪一步了"。这在 2–3 小时后必然出错。

Aegis 把这个判断权收归到 [scripts/planctl](../scripts/planctl)：

- 当前应执行哪个 phase，**不由 AI 判断**，而是 `planctl next` 返回
- 依赖是否满足，**不由 AI 判断**，而是 `--strict` 模式校验 `depends_on`
- 是否完成，**不由 AI 判断**，而是 `plan/state.yaml` 里有没有这条记录

结果：AI 的角色被降级为"执行器"，而不是"调度器"。调度器稳定，AI 就不会乱。

### 2. 合同分层：phase plan 管"是什么"，execution 管"能改什么"

每个阶段有两份文档（见 [plan/phases/](../plan/phases/) 和 [plan/execution/](../plan/execution/)）：

| 文件 | 职责 | 作用 |
|------|------|------|
| `phase-X.md` | 阶段定位、目标、范围、完成判定 | 防止目标漂移 |
| `execution/phase-X.md` | 允许改动、禁止改动、交付检查、裁决规则 | 防止实施越界 |

这两层分离很关键：AI 在实施时天然会"顺手多改一点"，execution 文档中的"本次不要做"和"裁决规则"**直接把越界判死**，不给自由发挥空间。

### 3. 严格的上下文装载顺序（压缩控制的核心）

[plan/manifest.yaml](../plan/manifest.yaml) 里声明了一条硬规则：

```yaml
compression_control:
  rules:
    - 永远不要一次性加载所有 phase 文档。
    - 只在当前 phase 读取 plan/common.md、当前 phase plan 和当前 phase execution。
```

每个 phase 的 `required_context` 固定为三份：

1. `plan/common.md`（全局硬约束，不变项）
2. 当前 phase 的 plan（本阶段定位）
3. 当前 phase 的 execution（本次边界）

这意味着：**不管项目多大，当前工作窗口始终只装 3 份文档。** 上下文窗口永远够用，AI 的注意力不会被未来或过去的阶段污染。

### 4. 闭环循环：每个 phase 都是一次"小型完整工作单元"

标准循环（见 [plan/workflow.md](../plan/workflow.md)）：

```
next → 读 required_context → 实施 → complete → handoff --write → next
```

每一圈结束时有三个"硬化"动作：

- `planctl complete` 写入 [plan/state.yaml](../plan/state.yaml) — **完成成为事实**
- `planctl handoff --write` 刷新 [plan/handoff.md](../plan/handoff.md) — **恢复锚点就位**
- 下一圈 `next` 自动推进 — **无需人类介入**

这就把"5 小时的长任务"切成了 **N 个互不影响的 30–60 分钟短任务**，每一段都可以独立开始、独立结束、独立恢复。

### 5. 压缩恢复：固定三步，不依赖聊天历史

当 AI 被压缩或换会话，常规做法是让它"读一下之前聊了什么"——这几乎一定会出错。Aegis 的恢复协议就三步：

1. 读 `plan/manifest.yaml`（知道流程长什么样）
2. 读 `plan/handoff.md`（知道上一步到哪）
3. 跑 `planctl next --strict`（知道下一步做什么）

**恢复后的 AI 和压缩前的 AI 拿到的信息几乎一样。** 这是连续工作能跨越压缩边界的关键。

### 6. 用机器可执行的检查替代"感觉完成"

完成判定里不是"你觉得做好了吗"，而是：

- `planctl complete` 会再跑一次 `depends_on` 校验
- execution 文档里列着可逐项勾选的"交付检查"
- 仓库级指令（[.github/copilot-instructions.md](../.github/copilot-instructions.md) 第八节）要求"未写入 state.yaml 的 phase 不视为完成"

AI 自欺欺人的空间被压到接近 0。

### 7. 仓库级指令把规约变成"执行前置"

[.github/copilot-instructions.md](../.github/copilot-instructions.md) 不是建议，而是**在 AI 开始工作前就注入主提示**的硬约束。它的第三节"开始实施前的强制步骤"规定：在写任何代码之前必须先跑 resolver。这就堵死了"AI 上来就直接动手"这条最常见的失败路径。

## 二、抽象 workflow：可复用到任何长任务项目

把 Aegis 的做法抽象成一套通用方法论，核心是 **7 个设计原则 + 1 个执行循环**。

### 设计原则

| # | 原则 | 对应的反模式 |
|---|------|-------------|
| P1 | **状态外部化**：所有"我在哪一步"的信息写到仓库文件，不依赖聊天记忆 | 靠 AI 记住进度 |
| P2 | **调度与执行分离**：用确定性脚本决定"做什么"，AI 只负责"怎么做" | AI 既当导演又当演员 |
| P3 | **三文件上下文律**：任何时刻只装 `全局约束 + 阶段定位 + 本次边界` 三份文档 | 一次性灌入整份 plan |
| P4 | **双层合同**：阶段目标（是什么）与执行边界（能改什么）分开描述 | 单文档既说目标又说步骤，AI 越界 |
| P5 | **依赖强制校验**：顺序由 `depends_on` + strict 模式守护，不信任直觉 | "前面应该差不多了吧" |
| P6 | **完成即写入**：`complete` 写 state，`handoff` 写锚点，两个动作缺一不继续 | 口头宣告完成 |
| P7 | **固定恢复协议**：压缩后恢复只有"manifest → handoff → next"三步 | 让 AI 回看聊天历史 |

### 标准执行循环

```
┌─────────────────────────────────────────────────────────┐
│  [0] 开局：读 manifest + handoff，跑 next --strict      │
└──────────────────────────┬──────────────────────────────┘
                           ↓
┌─────────────────────────────────────────────────────────┐
│  [1] 装载三文件：common + phase.plan + phase.execution  │
└──────────────────────────┬──────────────────────────────┘
                           ↓
┌─────────────────────────────────────────────────────────┐
│  [2] 实施：严格遵守 execution 的"允许/禁止/交付检查"    │
└──────────────────────────┬──────────────────────────────┘
                           ↓
┌─────────────────────────────────────────────────────────┐
│  [3] 自检：逐项过交付检查；不过关就不完成               │
└──────────────────────────┬──────────────────────────────┘
                           ↓
┌─────────────────────────────────────────────────────────┐
│  [4] 写回：complete --summary --next-focus              │
└──────────────────────────┬──────────────────────────────┘
                           ↓
┌─────────────────────────────────────────────────────────┐
│  [5] 刷新锚点：handoff --write                          │
└──────────────────────────┬──────────────────────────────┘
                           ↓
        ┌─────────── 还有下一 phase？ ────────────┐
        是                                        否
        ↓                                          ↓
   回到 [0]                                  任务真正结束
```

**压缩/新会话中断时，从 `[0]` 插入即可继续，无损。**

### 给其他项目落地这套 workflow 的清单

如果要把它搬到别的项目，需要产出以下最小件数：

1. **manifest**（一份 YAML/JSON）：声明 phase 顺序、depends_on、每个 phase 的 plan 与 execution 路径、required_context
2. **common 约束**（一份 Markdown）：长期不变的硬约束，所有 phase 都必带
3. **每 phase 两份文档**：
   - `phases/phase-X.md`：定位、目标、范围、完成判定、明确不做
   - `execution/phase-X.md`：允许改动、禁止改动、交付检查、裁决规则
4. **调度脚本**（对应 `planctl`）：提供 `resolve / next / status / complete / handoff` 五条命令，其中 `next/resolve` 必须支持 `--strict` 依赖校验
5. **state 文件**：记录已完成 phase、时间戳、summary、next_focus
6. **handoff 文件**：记录当前状态、最近完成、下一 phase、下一步读取顺序、压缩恢复三步
7. **仓库级 AI 指令**（`.github/copilot-instructions.md` 或等价物）：把"先跑 resolver / 不跳依赖 / 不全量装载 / 完成才算完成"写成硬指令，注入到每一次对话开头

---

## 三、一句话总结

它能驱动 AI 工作 5 小时，不是因为它"写得详细"，而是因为它**把长任务里最容易出错的三件事——记忆进度、判断完成、压缩恢复——全部搬到了仓库文件和脚本里**；AI 在每一圈只面对一个小得足以稳定执行的窗口，做完立刻写回事实，下一圈从外部状态读出而不是从记忆里捞。于是 5 小时变成了 8 次独立的 40 分钟，而不是一次 5 小时的记忆马拉松。
